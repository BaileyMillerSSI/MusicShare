# Authenticated status draft

The canonical route is HTTPS `GET /status` on the existing Next.js frontend host. It is a Node server route, not browser JavaScript or a public API/backend exposure. Aspire internal API, MongoDB, RabbitMQ and providers remain private. No live URL or successful deployment is asserted by this draft.

Provision the variables in `status.env.example` as frontend runtime secrets only after activation approval. Tokens must be 32–256 base64url characters; Authorization headers over 512 characters are rejected before hashing. Invalid configured tokens and an empty current token fail closed with 503; invalid/missing credentials return 401. Send only `Authorization: Bearer <token>` over HTTPS. Rotation accepts current and previous tokens together; remove previous after the overlap. Never put tokens in URLs, public build variables, logs or source. Existing HTTPS ingress must terminate TLS; the route does not trust client-supplied forwarding headers or redirect credentials. No Azure management access is needed.

Successful responses follow the shared [status v2 contract](../contracts/status-v2/README.md) and report only the responding web process. They do not probe API, workers, database, queues or music providers. Existing Development-only backend health/alive endpoints are not assumed available in production. HEAD uses the same authentication and cache headers with no body or probes. No dependency work occurs before or after authentication; response size is fixed and bounded. Immediately after provisioning and before `azd deploy` builds the application, the existing main deployment workflow writes the exact checked-out SHA, UTC build preparation time, and producing GitHub workflow run to a server-only file. This timestamp is not deployment completion. Local builds retain null SHA/time and omit workflow. Version and deployment metadata remain null. Request time is only sampledAt.

All responses disable browser/CDN caching and enable no CORS. The service worker explicitly excludes /status. The endpoint-only rollout wires the approved GitHub production secret STATUS_TOKEN_CURRENT through AZURE_STATUS_TOKEN_CURRENT and the Aspire status-token-current parameter to the frontend runtime. It does not include scanner workflows or activate BL polling. Existing CI deploys only from main; the endpoint-only branch may deploy through that existing pipeline after review, CI and credential approval.

Deployment preflight validates the configured token without printing it and fails before Azure login/provisioning if absent or malformed. No default token is supplied. Both existing provisioning and deployment steps receive the same GitHub environment secret; later deployments must retain that configured secret. Local development and ordinary tests do not require the publish-only Aspire parameter.
